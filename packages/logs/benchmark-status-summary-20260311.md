CPU、内存采样趋势（重点）：
- RSS 均值大致稳定在 **54–55MB**（max 约 55.3MB），无明显随时间上升趋势。
- `mem%` 峰值约 **0.20%**，`cpu%` 峰值约 **0.6%–0.7%**。
- 由于使用内进程注入方式，CPU 利用率较低，采样到的资源波动有限。

## 2) 现状归纳（当前能力判断）

1. 稳定性：全部 7 段均 `success == iterations`，无失败（5xx/4xx 或脚本异常未见）。
2. 容量：在当前测试方式下，吞吐峰值大致在 `~14.6 req/s`（阶段 2），后续并发继续提高后吞吐不再明显上升（出现饱和迹象）。
3. 延迟：p95 随负载上升明显增加，从 100ms 级别平滑增长到 600ms 级别后继续上升，说明延迟与扫描规模/并发压力相关。
4. 资源利用：在单机本地脚本压测下，内存表现稳健，无明显泄漏迹象，但该结果偏“乐观”。

结论：
- **对“最低负载压测 + 低影响观测”目标，当前已完成且达标。**
- 当前结果可作为后续对比基线。

## 3) 当前项目能力与已知边界

可验证能力：
- API 扫描路由 `scan` 已支持固定 payload（`packages/api/scripts/scan-benchmark.ts`）的重复调用。
- 可进行基准化参数化测试（`--files`, `--iterations`, `--concurrency`）。
- 可复用 `MAX_SCAN_DURATION_MS`、`MAX_FILES_PER_SYNC_SCAN` 环境变量控制扫描行为。

边界约束（当前压测观测）：
- 采用 `app.inject` 导致吞吐/CPU 不一定等价于真实网络部署。
- 采样窗口为 1 秒，进程短时/瞬时抖动可能被稀释。
- 单次 run 是“本地扫描器 + 规则最小集”路径，未覆盖复杂规则链、真实租户鉴权全链路和外网网络抖动场景。

## 4) 规划与待办（建议）

### 4.1 立刻补齐（建议优先）
- 建立“固定评估阈值”：
  - `success = iterations`
  - `p95 <= 600ms`（或按业务定义分级）
  - 采样期间 RSS 不长期单调上升
- 补 2 条对照：
  - `concurrency=1,2` 在同等 `files/iterations` 下作为保守线
  - `files=3000, iterations=200, concurrency=2/3` 验证真正临界点
- 输出统一的压测结果汇总模板（表 + 结论字段 + 合格判定）

### 4.2 下一阶段可提升
- 改为真实 HTTP 模式（启动服务端口）再压测，以模拟并发网络开销。
- 加入并发控制之外的队列/排队模型指标（等待时间、队列长度、超时率），确认瓶颈是否在扫描耗时还是路由排队。
- 将采样升为 500ms/1s 双速率并增加 RSS/heapUsed（`process.memoryUsage`）指标，提升趋势分辨率。
- 按负载曲线找到“拐点”后，在该附近做更细粒度扫掠（如 `files=2200/2300/2400`）。

### 4.3 长期优化
- 结合 `MAX_FILES_PER_SYNC_SCAN` 阈值与异步任务机制，评估分片扫描/任务拆分能力。
- 引入规则复杂度维度（文件类型、规则命中率、AST 复杂度）作为独立压测变量。
- 将日志标准化为 CI 可用的可视化输入（CSV/JSON schema 一致化、指标告警阈值）。
